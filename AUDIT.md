# AUDIT.md — Независимый аудит SoloLevelingBot (бот + лендинг)

Дата аудита: 2026-07-08.
Объект: Telegram-бот (aiogram 3, aiosqlite/SQLite WAL, APScheduler, Gemini API, Telegram Stars) + лендинг (Next.js 16, Tailwind v4).
Общий объём: ~3 600 строк. Код в целом аккуратный, читаемый, с продуманными мелочами (замок дня, атомарный `mark_quest_done`, fallback-модели Gemini). Ниже — всё, что мешает считать продукт готовым.

Приоритеты: **P0** — блокер запуска, **P1** — важно для качества, **P2** — можно отложить.

---

## 1. Архитектура и качество кода

### 1.1. [P1] Дублирование логики «смены дня» между scheduler и handlers
- **Что не так:** `scheduler.daily_rollover` и `handlers/helpers.process_day_events` содержат две параллельные копии одной и той же последовательности сообщений (HP_LOSS → DEATH → NEW_DAY → MILESTONE → GATE). В `daily_rollover` при этом **не отправляется** `STREAK_FROZEN` и не вызывается `notify_xp_events` для milestone-XP — поведение уже разошлось.
- **Почему важно:** любое изменение механики дня надо править в двух местах; расхождения уже есть.
- **Фикс:** вынести «отрендерить события DayEvents в список сообщений» в одну функцию (например, `game.day_events_messages(events) -> list[str]`) и использовать её и в шедулере, и в хендлерах.

### 1.2. [P1] `_pending_titles` в `handlers/custom.py` — состояние в глобальном dict вместо FSM
- **Что не так:** название добавляемого квеста хранится в модульном словаре. Теряется при рестарте, не работает при >1 процессе, утекает по памяти (нет TTL), в то время как рядом в `report.py` используется нормальный aiogram FSM.
- **Фикс:** перевести `/addquest` на FSM (`StatesGroup`), как `/report`.

### 1.3. [P1] `report_received`: потеря приростов статов из-за stale-строки пользователя
- **Что не так:** `stat_bumps = {s: user[s] + 1 for s in stats}` вычисляется по строке `user`, прочитанной **до** `grant_xp`. Если `grant_xp` дал левелап и увеличил какой-то стат, `update_user(**stat_bumps)` перезапишет его старым значением +1 — прирост от левелапа теряется.
- **Фикс:** либо перечитать пользователя после `grant_xp`, либо (лучше) писать инкрементально: `UPDATE users SET stat = stat + 1`.

### 1.4. [P1] `grant_xp` — неатомарный read-modify-write
- **Что не так:** XP/уровень/статы читаются из переданной строки `user`, модифицируются в Python и пишутся абсолютными значениями. Два параллельных `grant_xp` для одного пользователя (двойной тап по разным квестам, отчёт + квест) теряют часть XP/статов. Соединение с БД одно, но между `SELECT` и `UPDATE` есть `await`-точки (в т.ч. поход к боссу).
- **Фикс:** пер-пользовательский `asyncio.Lock` вокруг `grant_xp` (по аналогии с `_day_locks`) либо инкрементальные SQL-апдейты + пересчёт левелапов в транзакции.

### 1.5. [P2] `_day_locks: defaultdict(asyncio.Lock)` растёт бесконечно
- **Фикс:** периодическая очистка или `WeakValueDictionary` / LRU.

### 1.6. [P2] ✅ ИСПРАВЛЕНО (сессия 8) `notify_xp_events`: `BOSS_KILLED_BROADCAST` — не broadcast
- **Как исправлено:** константа переименована в `texts.BOSS_FINAL_BLOW` — она честно уходит только добившему («последний удар — твой»). Настоящую рассылку по рейду делает фоновая выдача наград: `texts.BOSS_REWARD` получает каждый из `db.boss_participants` с троттлингом `_safe_send`. См. 6.4.
- **Что было не так:** сообщение «босс повержен» получает только игрок, нанёсший последний удар. Остальные узнают только в воскресенье. Имя константы вводит в заблуждение.
- **Фикс:** при убийстве босса ставить флаг и рассылать всем (через очередь/джоб), награды выдавать сразу (см. 6.4).

### 1.7. [P2] Смешение слоёв: хендлеры ходят напрямую в `db.*` и в `game.*`
- **Что не так:** бизнес-логика размазана (лимиты отчётов — в хендлере, рефералка — в хендлере, премиум-продление — в хендлере платежей). Тестировать можно только через хендлеры.
- **Фикс:** постепенно вынести домены (referrals, premium, reports) в сервисные модули. Не блокер — кодовая база маленькая.

### 1.8. [P2] Мусор в репозитории
- `__pycache__/` и `.pyc` закоммичены; `tests/` использует `sys.path.insert` вместо пакетной структуры; `README` упоминает `solo.db`, а по факту `hunter.db`.
- **Фикс:** `.gitignore` для `__pycache__`, `*.py[cod]`, `*.db*`; поправить README.

## 2. Безопасность

### 2.1. [P0] Файлы БД с пользовательскими данными в репозитории
- **Что не так:** `hunter.db`, `hunter.db-shm`, `hunter.db-wal` лежат в корне проекта и не игнорируются. WAL-файл на 173 КБ содержит реальные данные (тексты отчётов пользователей, user_id, имена).
- **Почему важно:** утечка персональных данных при публикации репозитория; тексты ИИ-отчётов — приватный контент.
- **Фикс:** удалить из репозитория (и из истории git — `git filter-repo`), добавить `*.db`, `*.db-shm`, `*.db-wal` в `.gitignore`, вынести файл БД из корня проекта (например, `data/`).

### 2.2. [P0] `.gitignore` не покрывает `.env`
- **Что не так:** `config._load_env_files()` читает `.env`, `.env.local`, `.env.development.local`, но в `.gitignore` есть только `.env*.local`. Обычный `.env` с `TELEGRAM_BOT_TOKEN` и `GEMINI_API_KEY` будет закоммичен.
- **Фикс:** добавить `.env` и `.env*` в `.gitignore`; при подозрении, что токены уже попадали в историю — ротировать оба ключа.

### 2.3. [P1] Gemini API-ключ передаётся query-параметром `?key=`
- **Что не так:** ключ попадает в URL — логи прокси, access-логи, трейсы httpx при ошибках.
- **Фикс:** передавать через заголовок `x-goog-api-key`.

### 2.4. [P1] Prompt injection в ИИ-отчётах
- **Что не так:** текст пользователя вставляется в запрос как есть; системный промпт просит «не поддаваться», но модель можно уговорить ставить max XP. Потолок 120 XP ограничивает урон, но премиум-множитель x1.5 и 3 отчёта/день позволяют фармить до 540 XP/день чистым текстом.
- **Фикс:** серверная пост-валидация (уже есть clamp — хорошо), плюс: эвристика на повторяющиеся отчёты (сравнение с последними N отчётами), логирование подозрительных вердиктов, опционально второй дешёвый запрос-классификатор «это инъекция?».

### 2.5. [P2] Динамический SQL в `db.count_where` и `db.update_user`
- **Что не так:** имена таблиц/колонок �� `where`-фрагменты интерполируются f-строкой. Сейчас все вызовы внутренние и безопасные, но это заряженное ружьё: первый же вызов с пользовательским вводом = SQL-инъекция.
- **Фикс:** whitelist допустимых колонок в `update_user`; заменить `count_where` на явные функции.

### 2.6. [P2] Нет rate limiting на команды
- **Что не так:** любой пользователь может слать сотни `/quests` в секунду — каждый вызов порождает несколько SELECT + отправку сообщений. DoS-вектор на SQLite и на лимиты Bot API.
- **Фикс:** throttling-middleware (например, токен-бакет на user_id).

## 3. Надёжность и масштабируемость

### 3.1. [P0] `daily_rollover` без изоляции ошибок и без rate limit
- **Что не так:** цикл по всем пользователям: (а) исключение в `game.ensure_today` для одного пользователя прерывает весь ночной проход — остальные не получат квесты и штрафы; (б) на пользователя уходит до 4–5 сообщений подряд без задержки — при >30 msg/sec Telegram начнёт отдавать 429, `_safe_send` их молча съест, и часть пользователей не получит «Новый день».
- **Фикс:** обернуть тело цикла в try/except с логированием per-user; добавить троттлинг (~20 msg/sec суммарно, обработка `TelegramRetryAfter` с ожиданием `retry_after`); то же для `weekly_report`, `streak_danger`, `boss_low_hp_alert`, `winback`.

### 3.2. [P1] Гонка win-back бонуса в `ActivityMiddleware`
- **Что не так:** два апдейта подряд (сообщение + callback) читают `user` до того, как первый успел сбросить `winback_sent` → бонус начислится дважды. Сброс флага стоит до начисления, но чтение — до сброса.
- **Фикс:** атомарный `UPDATE users SET winback_sent = 0 WHERE user_id = ? AND winback_sent = 1` и начислять бонус только если `rowcount > 0`.

### 3.3. [P1] Стрик переживает даунтайм бота / многодневное отсутствие
- **Что не так:** `ensure_today` смотрит только квесты за `last_daily_date`, не проверяя, что это был вчерашний день. Если бот лежал 3 дня (или пользователь не заходил, а ночной джоб не отработал), при возврате пользователь получает `streak += 1`, как будто пропусков не было.
- **Фикс:** если `today - last_daily_date > 1 день` — считать промежуточные дни пропущенными (сброс/заморозка стрика, опционально без множественного HP-урона).

### 3.4. [P1] FSM на MemoryStorage — состояние теряется при рестарте
- **Что не так:** пользователь в середине `/report` после деплоя молча «выпадает» из диалога. При будущем масштабировании на 2+ процесса не работает вовсе.
- **Фикс:** для одного процесса — приемлемо, но зафиксировать осознанно; при росте — RedisStorage или SQLite-хранилище FSM.

### 3.5. [P1] ✅ ИСПРАВЛЕНО (сессия 6) Полные сканы всех пользователей каждую минуту
- **Как исправлено:** индексы `idx_users_reminder`, `idx_quests_date`, `idx_boss_damage_user` в `_SCHEMA`; `send_reminders` и `streak_danger` переведены на JOIN-агрегаты (`db.users_with_reminder_progress`, `db.users_in_streak_danger`) — один запрос вместо «выборка + квесты на каждого», фильтр по серии ушёл в SQL.
- **Осталось:** `daily_rollover`, `weekly_report` и `boss_low_hp_alert` по-прежнему грузят `all_users()` целиком — им нужна вся строка пользователя, так что здесь нужна курсорная/постраничная выборка, а не JOIN. Отдельная задача на фазу масштабирования.
- **Что было не так:** `send_reminders` раз в минуту делал `SELECT * FROM users WHERE reminder_time = ?` без индекса + для каждого — запрос квестов. `streak_danger`, `daily_rollover`, `winback` грузили `all_users()` целиком в память. До ~10 тыс. пользователей выживет, дальше — нет.

### 3.6. [P1] Нет транзакций вокруг составных операций
- **Что не так:** `damage_boss` — 3 запроса с одним `commit` в конце (это ок), но `grant_xp` + урон боссу + ачивки — серия независимых коммитов. Падение процесса посередине оставляет несогласованное состояние (XP начислен, урон боссу нет).
- **Фикс:** объединять связанные записи в явные транзакции (`BEGIN ... COMMIT`), критично для платежей и XP.

### 3.7. [P2] SQLite как потолок роста
- **Что не так:** одно соединение, один процесс, вертикальный потолок. Для MVP — правильный выбор, но нужно заранее спроектировать слой `db.py` так, чтобы миграция на Postgres не переписывала хендлеры.
- **Фикс:** сейчас — ничего; при >5–10 тыс. DAU — Postgres + пул. Слой `db.py` уже неплохо изолирован, сохранить это свойство.

### 3.8. [P2] `broadcast` блокирует обработку событий
- **Что не так:** рассылка на N пользователей с `sleep(0.05)` выполняется прямо в хендлере — на 10 тыс. пользователей это ~8 минут, в течение которых хендлер «висит» (polling-апдейты обрабатываются, но команда не отвечает, повторный запуск создаст вторую рассылку).
- **Фикс:** запускать рассылку как `asyncio.create_task` с защит��й от повторного запуска и прогрессом.

## 4. Тестирование и CI/CD

### 4.1. [P0] Нет CI вообще
- **Что не так:** нет GitHub Actions/аналога: тесты не запускаются автоматически, линтера нет, typecheck нет. Лендинг собирается с `ignoreBuildErrors: true` — TS-ошибки молча проглатываются.
- **Фикс:** минимальный CI: (1) `ruff check` + `ruff format --check`, (2) `pytest`, (3) `pnpm build` без `ignoreBuildErrors`, (4) `tsc --noEmit`.

### 4.2. [P1] Единственный тест — самописный smoke-скрипт, не pytest
- **Что не так:** `tests/test_smoke.py` — это `asyncio.run(main())` с asserts и `print`. Не интегрируется с pytest/CI, нет изоляции кейсов, падение одного assert прячет остальные. Не покрыты: платежи (successful_payment, продление премиума), рефералы (двойной заход, self-ref, порог 10), смерть/воскрешение, лимиты отчётов, парсер ответа Gemini (`_parse_json`), достижения, недельный сброс, награды босса.
- **Фикс:** мигрировать на pytest + pytest-asyncio с фикстурой временной БД; покрыть в первую очередь деньги (премиум-продление, идемпотентность платежа) и рефералку.

### 4.3. [P2] Нет тестов лендинга
- **Фикс:** достаточно build + одного smoke-теста рендера; e2e не нужен.

## 5. Деплой и эксплуатация

### 5.1. [P0] Нет процедуры деплоя и рестарта
- **Что не так:** README предлагает «python -m bot.main на любом VPS». Нет Dockerfile, нет systemd-юнита, нет авторестарта при падении, нет healthcheck. Упавший ночью процесс = все пользователи без квестов и напоминаний.
- **Фикс:** Dockerfile + docker-compose (или systemd unit с `Restart=always`); документированная процедура деплоя; volume для БД.

### 5.2. [P0] Бэкапы: README советует «просто копировать файл» — это некорректно для WAL
- **Что не так:** копирование `hunter.db` без `-wal` файла на живой базе даёт неконсистентный бэкап; автоматических бэкапов нет вообще. Потеря файла = потеря всех прогрессов и **оплаченных премиумов**.
- **Фикс:** cron-джоб с `sqlite3 hunter.db ".backup backup-$(date).db"` (или `VACUUM INTO`), выгрузка в объектное хранилище, ретеншн 7–30 дней; проверка восстановления.

### 5.3. [P1] Нет мониторинга и алертинга
- **Что не так:** ошибки только в stdout. Никто не узнает, что Gemini лёг, платежи не проходят или ночной джоб упал.
- **Фикс:** Sentry (или хотя бы уведомление админам в Telegram при исключениях уровня ERROR); метрики джобов («rollover обработал N пользователей за T секунд») в лог; алерт при 0 обработанных.

### 5.4. [P1] Нет защиты от двойного запуска инстанса
- **Что не так:** два процесса polling = конфликт getUpdates + двойные джобы шедулера (двойные штрафы HP, двойные напоминания). Легко словить при деплое без оркестрации.
- **Фикс:** file-lock/PID-lock на старте; graceful shutdown старого процесса до старта нового.

### 5.5. [P2] Логи без структуры и ротации
- **Фикс:** логирование в файл с ротацией или в journald; user_id в контексте записей.

## 6. Монетизация (Telegram Stars)

### 6.1. [P0] Платежи не сохраняются — невозможны возвраты и разбор споров
- **Что не так:** в `on_payment` не сохраняется `telegram_payment_charge_id`, сумма, дата, payload. Таблицы `payments` нет. Возврат Stars (`refundStarPayment`) требует charge_id — вернуть деньги пользователю технически невозможно. `/paysupport` обещает возвраты «по правилам Telegram Stars», но выполнять их нечем.
- **Почему важно:** это одновременно юридический (обязательства перед плательщиком), поддержкий и репутационный блокер.
- **Фикс:** таблица `payments (charge_id UNIQUE, user_id, payload, amount, created_at, refunded)`; писать в неё в `on_payment` до выдачи товара; админ-команда `/refund <charge_id>`.

### 6.2. [P0] Нет идемпотентности выдачи товара по платежу
- **Что не так:** если Telegram повторно доставит апдейт с `successful_payment` (ретраи бывают) — премиум продлится дважды/заморозка выдастся дважды; хуже: если бот упал между оплатой и `update_user`, пользователь заплатил и ничего не получил, и никакого следа нет.
- **Фикс:** уникальность по `charge_id` в таблице платежей + выдача товара только при первом INSERT (`INSERT OR IGNORE` → rowcount).

### 6.3. [P1] ✅ ИСПРАВЛЕНО (сессия 7) «Воскрешение» за 49 ⭐ невозможно купить тогда, когда оно нужно
- **Как исправлено:** введено состояние «при смерти» (колонка `dying_until`). HP ≤ 0 больше не убивает: охотник получает окно до конца дня с оффером `texts.DYING`, уровень и XP сохраняются. Смерть наступает на следующем rollover, только если HP осталось нулевым; если HP подняли (покупка или левелап) — `DYING_SURVIVED` и уровень цел. Покупка `revive` снимает `dying_until`, `PAY_REVIVE_DESC` переформулирован под реальную механику. Тесты — `tests/test_dying.py`.
- **Что было не так:** смерть происходит автоматически внутри `ensure_today` при смене дня — у пользователя нет момента «HP = 0, купи воскрешение, чтобы не потерять уровень». Описание товара («без потери уровня») не соответствует механике: к моменту покупки уровень уже потерян, товар фактически = «восстановить HP».
- **Почему важно:** это главный монетизационный триггер (loss aversion), и он не работает; плюс описание вводит в заблуждение (риск жалоб на платёж).
- **Фикс:** при HP ≤ 0 не убивать сразу, а переводить в состояние «при смерти» с окном (например, до конца дня): показать оффер «Воскрешение 49 ⭐ — сохрани уровень», по истечении окна — смерть. Либо честно пер��именовать товар в «Полное лечение».

### 6.4. [P1] ✅ ИСПРАВЛЕНО (сессия 8) Награды за босса приходят только в воскресенье
- **Как исправлено:** `handlers/helpers.notify_side_effects` при `result.boss_killed` вызывает `scheduler.spawn_boss_rewards(message.bot)` — выдача идёт фоновым таском, добивший не ждёт рассылку по всему рейду. Право на выдачу занимается атомарно (`db.claim_boss_rewarded`: `UPDATE ... WHERE rewarded = 0`) ДО начисления, поэтому воскресный `distribute_boss_rewards` из `weekly_report` остаётся страховкой и выходит на первом `return`. Дедуп живых тасков — `scheduler._reward_tasks` по ключу недели. Тесты — `tests/test_boss_rewards.py`, 11 кейсов.
- **Что было не так:** босс может быть убит в понедельник, а `distribute_boss_rewards` вызывается только из `weekly_report`. Неделя без обещанной награды убивает мотивацию рейда (и доверие — «где мои XP?»).
- **Фикс:** выдавать награды сразу при `boss_killed` (фоновым таском), в воскресенье — только страховочная проверка.

### 6.5. [P1] Нет конверсионных точек входа в премиум
- **Что не так:** `/premium` живёт только как команда в «⚙ Ещё». Нет апселла в моменты боли: при упоре в лимит отчётов (`REPORT_LIMIT` не содержит кнопку покупки), при упоре в лимит личных квестов, при потере стрика (не предлагается заморозка), в профиле.
- **Фикс:** inline-кнопка «Стать Монархом» прямо в ��ообщениях о лимитах; кнопка «Заморо��ка 25 ⭐» в предупреждении `STREAK_DANGER` и в сообщении о сгоревшем стрике.

### 6.6. [P2] Рефералы — накрутка бесплатного премиума
- **Что не так:** 10 регистраций по реф-ссылке = 7 дней премиума. Нет никакой проверки на фейковые аккаунты (мгновенные регистрации без активности). +100 XP обоим тоже фармится ботами.
- **Фикс:** засчитывать реферала только после активации (например, выполнил 3 квеста или прожил 2 дня); анти-фрод порог по скорости регистраций.

### 6.7. [P2] `is_premium` fallback на легаси-флаг
- **Что не так:** `is_premium()` при пустом `premium_until` верит колонке `is_premium`, которая выставляется в 1 при покупке и никогда не сбрасывается. Если когда-нибудь `premium_until` окажется пустым при `is_premium=1` — вечный премиум.

## 7. Продукт и рост

### 7.1. [P1] Одна временная зона на всех (Europe/Moscow)
- **Что не так:** «день» кончается в полночь по Москве для всех. Пользователь из Владивостока получает штраф в 7 утра своего дня; из Европы — в 22:00. Напоминания «20:00» — тоже по МСК. Для продукта про ежедневную дисциплину граница дня — ядро механики.
- **Фикс:** колонка `tz` у пользователя (настройка при онбординге /remind-подобной командой или геолокацией), все расчёты `today_str`/roll-over — по TZ пользователя.

### 7.2. [P1] Онборд��нг обрывается после первого квеста
- **Что не так:** новичок получает первый квест с кнопкой — отлично. Но дальше нет ведения: не объясняются отчёты (`/report` — ключевая AI-фича), босс, стрики. `ONBOARDING_FIRST_DONE` — конец воронки.
- **Фикс:** цепочка онбординга на 2–3 дня (day-1: покажи /report c примером; day-2: босс и рейтинг; day-3: рефералка) через шедулер.

### 7.3. [P1] Вирусный контур слабый
- **Что не так:** карточка с QR — единственный share-механизм, и она не подталкивает делиться (нет кнопки «поделиться», нет share-текста). Реф-ссылка спрятана в `/ref`. Нет реакции «мой друг достиг ранга C» и т.п.
- **Фикс:** кнопка «Поделиться карточкой» (switch_inline_query / prepared inline message), реф-ссылка в подписи карточки, milestone-сообщения с готовым share-текстом.

### 7.4. [P2] Квесты не персонализируются и не прогрессируют
- **Что не так:** `random.sample` из общего пула — на 60-й день пользователь S-ранга получает те же «выпей 2 литра воды». Нет выбора направлений (спорт/учёба) при онбординге, сложность не растёт с уровнем.
- **Фикс:** теги-предпочтения при онбординге; масштабирование сложности/XP от уровня; исключение недавно выданных квестов.

### 7.5. [P2] Смерть — чрезмерно карательная механика для habit-продукта
- **Что не так:** минус уровень + обнуление XP за пропущенные дни — сильный триггер к churn («всё пропало — удаляю бота»). Исследования habit-приложений показывают, что жёсткие наказания усиливают отток после первого срыва.
- **Фикс:** A/B-мягчение: смерть сохраняет часть XP; «щит новичка» — первые 7 дней смерть невозможна.

### 7.6. [P2] Нет аналитики продукта
- **Что не так:** `/admin` показывает DAU/WAU — хорошо, но нет ретеншн-когорт, воронки онбординга, конверсии в оплату. Решения по продукту принимать не на чем.
- **Фикс:** таблица событий (`events: user_id, name, ts`) + простые когортные запросы в `/admin`.

## 9. Юридическое / комплаенс

### 9.1. [P0] Нет политики конфиденциальности и условий использования
- **Что не так:** бот собирает ПД (Telegram ID, имя, username, тексты отчётов — потенциально чувствительные записи о жизни пользователя) и принимает платежи, но нет ни privacy policy, ни terms. Telegram для платёжных ботов требует поддержку (`/paysupport` есть — хорошо) и прозрачные условия; для аудитории РФ актуален 152-ФЗ, для ЕС — GDPR.
- **Фикс:** страницы `/privacy` и `/terms` на лендинге + команды/ссылки в боте (`/privacy`); в текстах — что храним, зачем, сколько, что отчёты отправляются в Google Gemini.

### 9.2. [P1] Нет удаления данных по запросу
- **Что не так:** права на удаление (GDPR art. 17 / 152-ФЗ) реализовать нечем — нет команды и нет процедуры.
- **Фикс:** команда `/delete_me` с подтверждением: удаление user + quests + reports + achievements + boss_damage (платежи — оставить обезличенно для бухгалтерии).

### 9.3. [P1] Тексты отчётов уходят в Gemini без явного уведомления
- **Фикс:** дисклеймер при первом `/report` («текст будет обработан ИИ Google Gemini») + пункт в privacy policy.

### 9.4. [P2] Торговая марка Solo Leveling
- **Что не так:** название бота, имена боссов (Игрис и др.), терминология — IP правообладателя (Kakao/D&C Media). Футер лендинга честно пишет «фанатский проект» — хорошо, но монетизация фан-проекта повышает риск претензий.
- **Фикс:** юридически безопаснее — постепенный ребрендинг в «вдохновлено жанром» с собственными именами; минимум — дисклеймер и в боте (/help), готовность к переименованию.

### 9.5. [P2] Условия возвратов не определены
- **Что не так:** `/paysupport` обещает возвраты «в течение разумного срока» — неопределённое обязательство.
- **Фикс:** явная политика (например, «возврат в течение 48 часов, если премиум не активировался»), после реализации 6.1.
